## 三、面试高频问题梳理

### 3.1 项目整体理解

**Q1: 简单介绍一下这个项目?**

回答框架:
> 这是一个 PCB 自动光学检测系统的上位机软件。PCB 在制造过程中会产生开路、短路、铜渣、针孔等缺陷,传统人工检测效率低、漏检率高。这套系统通过运动控制器驱动相机对 PCB 逐条扫描采图,然后用 Gerber 模板做特征匹配对齐,再用 YOLO 模型做缺陷检测,最终输出缺陷坐标和可视化结果。

**Q2: 系统的整体架构是怎样的?**

> 系统分为 7 层:
> - **核心抽象层**:定义了 PLC、ACS、相机、检测器、模板匹配、数据仓储 6 个 ABC 接口
> - **数据模型层**:Material、ScanRecord、DetectionParams 等 dataclass
> - **业务服务层**:MaterialService、ScanService、DetectionService、VacuumService 等,纯 Python 不依赖 Qt
> - **硬件实现层**:ModbusPlcClient、SpiiPlusAcsComm、ProcessCamera、SahiDetector、LoFtrTemplateMatcher
> - **数据持久化层**:SQLite + Repository 模式
> - **UI 层**:MVVM,ViewModel 持有业务逻辑,View 纯视图
> - **DI 容器**:Container 作为组合根,集中组装依赖

**Q3: 为什么选择 PyQt5 而不是 PySide6 / Electron / C# WPF?**

> - PyQt5 生态成熟,与 Python 深度学习生态无缝集成
> - 相比 Electron,PyQt5 是原生渲染,内存占用低,适合工控机资源受限环境
> - 相比 C# WPF,Python 可以直接调用 PyTorch/TensorRT,无需跨语言桥接
> - Qt 的信号槽机制天然适合多线程硬件交互场景

### 3.2 架构设计深究

**Q4: 什么是依赖注入?你的项目里怎么实现的?**

> 依赖注入(DI)是控制反转(IoC)的一种实现形式。传统代码是"高层直接 new 低层",DI 是"由容器创建低层实例并注入给高层"。
>
> 我的实现:
> - `core/container.py` 的 `Container` 类是组合根(Composition Root)
> - 每个 property 延迟创建实例并缓存(单例)
> - 服务层构造函数只接收接口类型参数,如 `MaterialService(material_repo: IMaterialRepository, config)`
> - UI 层通过 `container.material_service` 获取已组装好的服务
>
> 好处:
> - 业务层不依赖具体实现,可替换(如 SQLite 换成 PostgreSQL 只需新增一个 Repository 实现)
> - 可测试(单元测试用 Mock 注入)
> - 依赖关系集中可见

**Q5: 依赖倒置原则(DIP)在你的项目里体现在哪里?**

> DIP 要求"高层不依赖低层,二者都依赖抽象"。我的项目:
> - `core/interfaces/` 定义了 6 个 ABC 接口
> - `core/services/MaterialService` 只依赖 `IMaterialRepository` 接口,不知道具体是 SQLite 还是 JSON 实现
> - `hardware/ModbusPlcClient` 实现了 `IPlcClient` 接口
> - 依赖方向:ui → container → services → interfaces ← hardware/data
>
> 如果要替换 PLC 厂商,只需新增一个 `FakePlcClient(IPlcClient)` 实现,业务代码零改动。

**Q6: 为什么要引入状态机?之前怎么管理的?**

> 之前用散落的布尔标志位管理(`quick_start_running`、`vacuum_on`、`blower_on`、`start_sample_detection_running` 等),问题:
> - 状态组合爆炸,难以穷举所有合法状态
> - 容易出现非法状态转换(如检测中又点了开始)
> - 没有状态变化通知机制
>
> 状态机方案:
> - 11 个显式状态(IDLE → MATERIAL_SELECTED → CAMERA_STARTING → ... → FINISHED)
> - 14 条合法转换路径,非法转换抛 ValueError
> - 监听器模式,状态变化自动通知 UI
> - `is_running()` / `is_idle()` / `is_error()` 语义化查询

**Q7: MVVM 和 MVC 的区别?你的 ViewModel 和 View 怎么通信?**

> MVC 中 Controller 直接操作 View;MVVM 中 ViewModel 不知道 View 的存在,通过数据绑定/信号通知 View。
>
> 我的实现:
> - ViewModel 通过 `pyqtSignal` 发出通知(`material_data_changed`、`sensor_data_updated`、`error_occurred`)
> - View 连接这些信号到自己的更新方法
> - View 的用户事件(按钮点击)调用 ViewModel 的 `pyqtSlot`
> - ViewModel 不 import View,View 也不直接操作业务数据

**Q8: Repository 模式解决了什么问题?**

> 之前数据访问代码散落在 MyWindow 各方法里,直接读写 JSON 文件。问题:
> - 数据访问逻辑与业务逻辑耦合
> - 无法单元测试(依赖文件系统)
> - 切换存储方案需要改业务代码
>
> Repository 模式:
> - `IMaterialRepository` 接口定义 `get_all/get_by_id/save/delete`
> - `SqliteMaterialRepository` 实现具体 SQLite 访问
> - 业务层只依赖接口,测试时注入 Mock

### 3.3 多线程与并发

**Q9: 你的项目用了哪些多线程技术?**

> - **QThread**: ACS 运动线程(AcsThread)、PLC 轮询线程(PlcThread)、检测线程(MatchAndDetectThread)
> - **QThreadPool + QRunnable**: 并发检测任务,ImageProcessingWorker
> - **QProcess**: 调用 external_trigger 相机采图可执行文件,进程隔离
> - **threading.Timer**: 真空风机关闭延迟(VacuumService)
> - **Queue**: 生产者-消费者模式,ACS 采图入队,检测线程出队

**Q10: QThread 的 moveToThread 模式和继承 QThread 有什么区别?你用的哪种?**

> - 继承 QThread:重写 `run()` 方法,逻辑在子类中
> - moveToThread:创建 Worker 对象,`worker.moveToThread(thread)`,通过信号槽触发
>
> 我的检测线程用的是继承 QThread(MatchAndDetectThread),因为检测是一个长时连续任务。对于离散任务用 QRunnable + QThreadPool。
>
> moveToThread 的优势是一个 Worker 可以被多个线程复用,更灵活。如果重做,我会统一用 moveToThread。

**Q11: 线程间怎么通信?有什么坑?**

> 用 pyqtSignal 信号槽,Qt 保证跨线程的信号槽是线程安全的(通过事件队列)。
>
> 坑:
> - 不能在子线程直接操作 UI 控件,必须通过信号
> - 信号参数如果是自定义类型,需要注册 `qRegisterMetaType`(PyQt5 中一般用基础类型)
> - QThread.quit() 后要 wait(),否则资源泄漏

**Q12: QProcess 调用外部程序有什么优势?怎么通信?**

> 优势:
> - 进程隔离,相机程序崩溃不影响主程序
> - 可以调用非 Python 编写的程序(C/C++ SDK)
>
> 通信:
> - stdin 写命令:`proc.write(b"start\n")`
> - stdout/stderr 读输出:`readyRead` 信号 → `readAllStandardOutput()`
> - 退出流程:stop → 延迟 2 秒 exit → 延迟 4 秒 kill(确保优雅退出)

### 3.4 算法与深度学习

**Q13: 什么是 SAHI?为什么需要切片推理?**

> SAHI = Slicing Aided Hyper Inference。
>
> 问题:PCB 图像分辨率极高(3250 DPI 导出,单张可能上万像素),直接送入 YOLO 会 resize 到 640x640,小目标(如 10um 的针孔)在 resize 后只剩 1-2 像素,几乎无法检测。
>
> SAHI 方案:
> 1. 将大图切分为 1200x1200 的切片,相邻切片有 overlap(默认 5%)
> 2. 每个切片独立送入 YOLO 推理
> 3. 将所有切片的检测结果坐标变换回原图坐标系
> 4. NMS 去除重叠区域的重复检测
>
> 项目中用 `get_batched_sliced_prediction` 做批处理切片推理。

**Q14: EfficientLoFTR 是什么?和传统 LoFTR 比有什么优势?**

> LoFTR = Local Feature TRansformer,一种基于 Transformer 的无检测器(detector-free)特征匹配方法。
>
> EfficientLoFTR 改进:
> - 粗匹配用轻量级 Transformer 替代原始密集注意力,降低计算复杂度
> - 细匹配用更高效的结构
> - 精度持平或略优,速度提升数倍
>
> 项目中用于 Gerber 模板图与实拍样本图的特征点匹配,实现图像对齐。

**Q15: LightGlue 是什么?和 SuperGlue 比有什么优势?**

> LightGlue 是 SuperGlue 的改进版:
> - 自适应计算深度:容易匹配的图片提前停止计算,减少计算量
> - 更易训练,更快收敛
> - 推理速度比 SuperGlue 快 2-3 倍
>
> 项目中先用 ALIKED 提取特征点,再用 LightGlue 做特征匹配。

**Q16: TensorRT 加速原理是什么?你怎么用的?**

> TensorRT 是 NVIDIA 的推理优化引擎,优化包括:
> - 层融合(Layer Fusion):合并连续的 Conv+BN+ReLU
> - 精度校准:FP32 → FP16/INT8,减少显存和计算量
> - Kernel 自动调优:针对具体 GPU 选择最优 CUDA kernel
>
> 项目中 YOLO 模型先导出为 ONNX,再用 TensorRT 编译为 `.engine` 文件,13 种模型按 flag 切换:
> ```python
> model_paths = {
>     0: ".../best-1031.engine",
>     1: ".../best-30-95um-1207.engine",
>     ...
> }
> AutoDetectionModel.from_pretrained(
>     model_type="ultralytics",
>     model_path=model_paths[flag],
>     confidence_threshold=conf_threshold,
>     device="cuda"
> )
> ```

**Q17: 模型管理是怎么做的?为什么用单例?**

> `ModelManager` 单例 + 缓存:
> - 首次加载模型时从磁盘加载到 GPU,缓存到 `_model_cache` 字典
> - 缓存键由模型类型 + 参数(flag、conf_threshold、max_num_keypoints 等)组合
> - 后续相同参数请求直接返回缓存实例
>
> 用单例的原因:
> - 模型加载耗时(几秒到几十秒)
> - 模型占显存,不能重复加载
> - 多个检测线程共享同一模型实例

**Q18: 模板匹配的完整流程是什么?**

> 1. 从文件名提取编号(`extract_number_from_path`)
> 2. 如果是最后一张图(编号 == 模板数量),调用 `process_images` 处理
> 3. 否则打开对应编号的模板图
> 4. `linear_adjust_template` 对模板做线性调整(顶部裁剪偏移)
> 5. 粗匹配:`coarse_matching_first` 用 EfficientLoFTR 做粗对齐
> 6. 精匹配:`fine_matching_pillow_on_template_drew_return_bgr` 用 LightGlue + ALIKED 做精对齐
> 7. 返回叠加结果的 BGR 图像

### 3.5 硬件通信

**Q19: Modbus TCP 协议你了解多少?**

> Modbus 是工业通信协议,TCP 是其中一种传输方式:
> - **线圈(Coil)**:1 位布尔量,地址空间 000001-099999,用于开关量(真空/风机/报警)
> - **保持寄存器(Holding Register)**:16 位整数,地址空间 400001-499999,用于模拟量(温度/压力)
> - 浮点数占 2 个寄存器(32 位),用 `BinaryPayloadDecoder` 解码,需要指定字节序(BIG)和字序(LITTLE)
>
> 项目中 PLC 地址:线圈 100-256,寄存器 150-204。

**Q20: PLC 通信断了怎么办?**

> `ModbusPlcClient` 实现了自动重连:
> ```python
> def read_bits(self, address, count):
>     try:
>         result = self.client.read_coils(address, count)
>         if result.isError():
>             self.reconnect()
>             return self.read_bits(address, count)  # 递归重试
>         return result.bits
>     except Exception:
>         self.reconnect()
>         return self.read_bits(address, count)
> ```
> 连接时重试 3 次,每次间隔 5 秒。

**Q21: ACS 运动控制器是怎么控制的?**

> 通过 SPiiPlusPython SDK:
> - `OpenCommEthernetTCP(ip, port)` 建立连接
> - 运动程序以 buffer 文件形式加载:`run_buffer_from_file(conn, buffer_id, file_path)`
> - 不同运动操作对应不同 buffer:x_home(回零)、forward(前进采图)、backward(后退)等
> - buffer 文件是 ACS 控制器专用的运动脚本

### 3.6 工程化

**Q22: 你怎么做测试的?有什么不能测的?**

## 四、面试深究方向

### 4.1 软件设计深究

#### 4.1.1 分层架构的边界划分

**深究点**: 你的 7 层架构会不会过度设计?

> 回答策略:
> - 承认对小型项目可能过度,但 AOI 系统是长期维护的商用软件,需要可替换性
> - 举例说明:实际受益场景是"更换 PLC 厂商"或"从 JSON 迁移到 SQLite"时业务代码零改动
> - 如果是快速原型,可以只用 3 层(UI/Service/Data)

#### 4.1.2 依赖注入容器的实现细节

**深究点**: 你的 Container 是延迟创建,如果多个线程同时访问会怎样?

> 当前实现不是线程安全的。如果多线程同时首次访问同一 property,可能创建多个实例。
> 解决方案:
> - 加 `threading.Lock`
> - 或在应用启动时预初始化所有单例(eager initialization)
> - 或用 `functools.lru_cache`

#### 4.1.3 状态机的局限性

**深究点**: 你的状态机是手写的,为什么不用 transitions 库或 pytransitions?

> - 手写状态机更轻量,无外部依赖
> - 状态转换逻辑简单明确,11 状态 14 转换,手写更直观
> - 如果状态超过 30 个或需要嵌套状态机,会考虑用 transitions 库
>
> 局限性:
> - 不支持嵌套状态( hierarchical state )
> - 不支持并行状态( orthogonal regions )
> - 转换条件是静态的,不支持运行时条件守卫(guard)

#### 4.1.4 MVVM 在 PyQt5 中的局限

**深究点**: PyQt5 没有原生数据绑定,你的 MVVM 是不是名不副实?

> 确实不是严格的 MVVM(没有双向数据绑定)。更准确的说是 MVP-Passive View:
> - ViewModel 充当 Presenter
> - View 主动连接 ViewModel 的信号(类似 Observer)
> - 如果要真正的数据绑定,可以用 PyQQt5 的 Q_PROPERTY 或第三方库
>
> 但这种"信号驱动"的 MVP 在 PyQt5 生态中是主流做法,实用性强。

#### 4.1.5 错误处理策略

**深究点**: 你的服务层异常怎么传播到 UI?

> 当前策略:
> - Service 层不吞异常,向上抛
> - ViewModel 用 try/except 捕获,通过 `error_occurred` 信号通知 View
> - View 收到信号后弹 QMessageBox
>
> 改进方向:
> - 定义领域异常层次(PlcConnectionError / DetectionError / MaterialNotFoundError)
> - 引入 Result 类型(类似 Rust)替代异常,让错误显式化
> - 加重试策略(tenacity 库)

### 4.2 算法优化深究

#### 4.2.1 SAHI 切片推理的优化

**深究点**: 切片大小 1200x1200 怎么确定的?overlap 5% 够吗?

> - 切片大小权衡:太小 → 切片数量多,推理慢;太大 → 小目标仍然漏检
> - 1200 是经验值,基于 YOLO 输入 640 + 2x 降采样,1200 保证了即使 resize 到 640,小目标仍有足够像素
> - overlap 5% 是 SAHI 默认值,实际可能需要根据缺陷最小尺寸调整
> - 优化方向:自适应切片(根据图像内容动态调整切片位置,跳过空白区域)

**深究点**: 切片结果怎么合并?NMS 在跨切片边界怎么处理?

> SAHI 内部做了跨切片 NMS:
> 1. 所有切片检测结果坐标变换回原图
> 2. 全局 NMS(IoU 阈值通常 0.5)
> 3. 对于跨切片边界的物体,可能被两个切片都检测到,NMS 会保留置信度最高的
>
> 潜在问题:如果一个物体正好被切到两个切片各一半,两个切片都可能漏检。
> 解决:增大 overlap 或用无缝拼接推理(seamless tiled inference)。

#### 4.2.2 TensorRT 优化深究

**深究点**: FP16 和 INT8 的精度损失你怎么评估的?

> - FP16 通常精度损失 < 1%,可以接受
> - INT8 需要校准数据集,精度损失可能 3-5%,需要做 mAP 对比
> - 项目中检测用的是 FP16(.engine 文件),模板匹配用 FP32(精度要求高)

**深究点**: 动态 batch size 和动态分辨率你怎么处理?

> TensorRT 构建引擎时需要指定 profile:
> ```python
> profile = builder.create_optimization_profile()
> profile.set_shape("images", (1, 3, 640, 640), (8, 3, 640, 640), (16, 3, 640, 640))
> config.add_optimization_profile(profile)
> ```
> 项目中用的是固定 batch=1,固定 640x640,因为没有并发推理需求。如果要多图并行,需要动态 batch。

#### 4.2.3 特征匹配优化

**深究点**: EfficientLoFTR 的粗匹配阈值 0.015 怎么定的?

> - 阈值越低,匹配点越多,但误匹配也多
> - 0.015 是经验值,在 PCB 场景下平衡了匹配率和精度
> - 后续有 RANSAC 剔除外点,所以粗匹配可以宽松一些

**深究点**: ALIKED 和 SuperPoint 怎么选?

> - SuperPoint:经典方案,基于 homographic adaptation 训练,特征点均匀
> - ALIKED:较新,基于可微分检测器,特征点定位更准
> - 项目用 ALIKED + LightGlue,因为 LightGlue 对 ALIKED 有专门的预训练权重

**深究点**: 模板匹配的线性调整(linear_adjust_template)是什么?

> PCB 的 Gerber 文件导出的模板图和实际拍摄的图在 Y 轴方向可能有固定偏移(因为相机安装位置和 Gerber 原点不一致)。
> `linear_adjust_template` 对模板图做顶部裁剪(偏移量 9070 像素),补偿这个系统性偏差。
>
> 优化方向:这个偏移应该自动化标定,而不是硬编码。

#### 4.2.4 模型选型与训练

**深究点**: 为什么用 YOLO11 而不是 RT-DETR / DETR?

> - YOLO 系列推理速度快,适合实时检测
> - RT-DETR 精度更高但速度慢,PCB 检测对速度敏感
> - 项目里有 13 个模型,包括 .engine(TensorRT)和 .pt(PyTorch),按 flag 切换
>
> 优化方向:可以尝试 YOLO11-P2(小目标专用,有 P2 检测头),项目里 flag=12 就是 11s-P2

**深究点**: 你的训练数据怎么标注的?数据量多少?

> (如果没做过训练,如实说"模型是算法团队训练的,我负责部署集成")

> - 标注工具:CVAT / LabelImg

### 4.3 性能优化深究

**深究点**: 单板检测时间多少?瓶颈在哪?**

> (需要实际数据,以下是分析框架)
> - 采图:ACS 运动 + 相机触发,约 X 秒(受运动速度限制)

## 五、容易被问到的"坑"问题

### 5.1 Python 相关

**Q: Python 的 GIL 对你的多线程有影响吗?**
> - IO 密集型(PLC/ACS 通信)不受 GIL 影响,多线程有效
> - CPU 密集型(图像处理)受 GIL 限制,但 PyTorch/TensorRT 底层释放 GIL,所以推理不受影响
> - 如果纯 Python 图像处理,用 multiprocessing

**Q: dataclass 和普通类有什么优势?**
> - 自动生成 `__init__` / `__repr__` / `__eq__`
> - 类型注解,IDE 提示友好
> - `field(default_factory=list)` 避免可变默认值陷阱

**Q: ABC 抽象基类和 Protocol 有什么区别?**
> - ABC:运行时检查,子类必须显式继承
> - Protocol:结构化类型(鸭子类型),不需要显式继承,mypy 检查
> - 项目用 ABC 是因为需要运行时 isinstance 检查

### 5.2 Qt 相关

**Q: PyQt5 的信号槽是同步还是异步?**
> - 同队列:直接调用(同线程)
> - 跨队列:通过事件队列异步(QueuedConnection)
> - 自动判断:Qt.AutoConnection(默认)

**Q: QThread 为什么不能直接操作 UI?**
> - Qt 要求所有 UI 操作在主线程(GUI 线程)
> - 子线程操作 UI 会导致段错误
> - 必须通过信号槽(QueuedConnection)通知主线程

### 5.3 数据库相关

**Q: 为什么用 SQLite 而不是 MySQL/PostgreSQL?**
> - 嵌入式,无需独立服务进程
> - 单文件,部署简单
> - 读写性能足够(单机场景)
> - 如果要多机共享数据,需要换 MySQL

**Q: SQLite 有并发限制吗?**
> - 写操作是串行的(数据库级锁)
> - 读操作可以并发
> - 如果检测日志高频写入,可能需要 WAL 模式:`PRAGMA journal_mode=WAL`

## 八、项目最大难点与最大成就

> 本章基于项目实际代码梳理,非虚构。面试官问"这个项目最大的难点是什么""最大成就是什么"时参考此章。

### 8.1 最大难点:多硬件子系统的时序协同

系统要同时协调 **4 个独立硬件子系统** 在精确时序下工作:

```
PLC(100ms 轮询) ──光幕安全──┐
       │                     │
       ├─software_ready─→ ACS 运动 ──触发──→ 相机采图 ──入队──→ 检测线程
       │                     │                                    │
       └─真空/风机/报警 ←────┘←─────────────── 检测完成 ←────────┘
```

**为什么难?**

#### 1. 三个独立通信链路,三种不同协议

- **PLC**:Modbus TCP,线圈/寄存器,100ms 轮询(`main_window.py:167` `timer.start(100)`)
- **ACS**:SPiiPlusPython SDK,buffer 文件加载
- **相机**:QProcess 子进程,stdin 管道发命令(start/stop/exit)

三种链路的连接管理、错误处理、超时策略都不同,无法用统一方式处理。

#### 2. 时序耦合极紧

PLC 置 `software_ready=1` → ACS 启动运动 → 相机按步进触发采图 → 图片入队 → 检测线程消费。任何一个环节卡住,整条流水线停摆。

参考 `main_window.py:360-376` 的 `update_readings` 方法,100ms 内要完成:光幕检查 → 启动信号检查 → 真空状态判断 → 传感器读取 → UI 更新,且不能阻塞主线程。

#### 3. 故障传播复杂

- 光幕触发要立即停机报警(`main_window.py:361-364`,写 alarm_3/alarm_4)
- PLC 断线要自动重连(递归重试)
- 相机进程崩溃不能拖垮主程序(QProcess 进程隔离)
- 检测线程异常不能阻塞采图(独立 QThread + Queue 解耦)

#### 4. 状态一致性难保证

AB 面交替检测模式下,要同时维护十几个布尔/计数标志:
- `quick_start_running` / `vacuum_on` / `blower_on` / `start_sample_detection_running`
- `ab_cycle_count` / `current_ab_cycle` / `current_ab_folder`
- `blower_timer` 延迟关闭定时器
- `vacuum_status` / `last_click_time` / `time_interval_threshold`

这些标志散落在 God Object 里极易出错,某个标志忘记重置就会导致流程死锁。

**这正是重构引入状态机的根本原因**:把 11 个状态、14 条合法转换显式化,用 `is_running()` / `is_idle()` 替代散落的布尔标志,用非法转换抛 `ValueError` 杜绝"检测中又点了开始"这类错误。

### 8.2 最大成就

#### 成就 1:技术栈整合难度

这个项目**不是"调个 API"的增删改查系统**,而是要把 4 个完全不同领域的技术栈缝合到一个桌面应用里:

这些技术栈各自有各自的最佳实践和坑,把它们整合成一个稳定运行的系统本身就是成就。

#### 成就 2:架构重构的量化成果

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 最大单文件 | 2480 行 (AoiSystemMain.py) | 拆为 4 个模块 |

#### 成就 3:SAHI 切片推理的工程化落地

从 `ModelManger.py:103-145` 可以看到,系统支持 **13 种检测模型动态切换**:

```python
model_paths = {
    0: ".../best-1031.engine",           # TensorRT
    1: ".../best-30-95um-1207.engine",   # 30um 线宽
    3: ".../best-008f-1203.engine",      # 0.08mm 板

这不是简单地"调一个模型",而是:

- **缓存键**由模型类型 + flag + conf_threshold 组合,支持同模型不同参数并存
- **TensorRT engine 和 PyTorch .pt 混合**调度,通过 `AutoDetectionModel.from_pretrained` 统一接口

PCB 缺陷中 10um 级的针孔在 3250 DPI 的大图上直接送 YOLO 会漏检,**SAHI 切片推理解决了小目标检测问题**——这是算法工程化的体现。

### 8.3 诚实补充:还没解决的真实难点

如果面试官追问"还有什么没做好的",这些是真实存在的:

#### 1. WorkerThread.py 仍有 2600+ 行未完全重构

检测线程内部逻辑仍然复杂,只是包了一层 `hardware/detection/` 接口,内部还是调用老代码(`coarse_matching_first`、`fine_matching_pillow_on_template_drew_return_bgr` 等)。这是渐进式迁移的妥协——旧代码还在用,新接口只是门面。

#### 2. linear_adjust_template 的偏移量是硬编码

`WorkerThread.py:133` 的 `captured_img.crop((0, 1671, w, h))` 和 `loftr_template_matcher.py` 中的 9070 偏移量是写死的。这是相机安装位置和 Gerber 原点的系统性偏差,应该做自动化标定而不是硬编码。

#### 3. 没有 CI/CD 和自动化部署

TensorRT engine 不能跨 GPU 复用(不同 GPU 架构需要重新编译),每次换机器都要重新编译 `.engine` 文件,目前靠手动。缺少 Docker 镜像 + 版本管理。

#### 4. 容器不是线程安全的

`core/container.py` 的延迟创建时如果多线程同时首次访问同一 property,可能创建多个实例。需要加 `threading.Lock` 或改为应用启动时预初始化。

#### 5. PLC 递归重连有栈溢出风险

`PLCmodbus.py:27-38` 的 `read_bits` 失败后递归调用自身:
```python
def read_bits(self, address, count):
    try:
        result = self.client.read_coils(address, count)
        if result.isError():
            self.reconnect()
            return self.read_bits(address, count)  # 递归重试
        return result.bits
    except Exception as e:
        self.reconnect()
        return self.read_bits(address, count)  # 递归重试
```
如果 PLC 持续不可用,递归会耗尽栈空间。应改为迭代 + 最大重试次数。

#### 6. 缺少硬件心跳机制

当前 PLC 是 100ms 轮询,但没有主动心跳检测。ACS 和相机也没有连接状态监控,断线后只能等下次操作失败才发现。

#### 7. 缺少崩溃上报和远程诊断

工控机部署在现场,出问题只能靠现场人员看日志。没有远程日志上报、没有异常自动上报、没有远程升级能力。

### 8.4 面试话术建议

#### 问"项目最大的难点是什么"

## 十、技术深度问答补充

### 10.1 关于状态机

**Q: 你的状态机是手写的,为什么不成熟用 transitions 库?**

> 手写状态机更轻量,无外部依赖,11 状态 14 转换的规模手写更直观。transitions 库适合 30+ 状态或需要嵌套状态机的复杂场景。我的状态机局限是不支持嵌套状态和并行状态,转换条件是静态的不支持运行时 guard 条件。如果后续流程变复杂,会考虑迁移到 transitions。

**Q: 状态机的监听器模式怎么实现?异常怎么处理?**

> `add_listener(callback)` 添加回调到列表,`transition()` 后遍历调用。关键是监听器异常不能影响状态机本身,所以每个回调用 try/except 包裹,异常只记录日志不抛出。这保证了即使 UI 层回调报错,状态转换仍然成功。

### 10.2 关于 Modbus 协议

**Q: 浮点数怎么在 Modbus 里传输?**

> Modbus 寄存器是 16 位,浮点数是 32 位,占 2 个寄存器。用 `BinaryPayloadDecoder.fromRegisters(registers, byteorder=Endian.BIG, wordorder=Endian.LITTLE)` 解码,`BinaryPayloadBuilder` 编码。字节序是大端(高位在前),字序是小端(低字在前)。项目里温度、压力、湿度都是这样读的。

**Q: 为什么线圈和寄存器地址空间是独立的?**

> 这是 Modbus 协议设计,线圈(coil)是 1 位布尔量用于开关量,保持寄存器(holding register)是 16 位整数用于模拟量。两者地址空间独立,所以 `config.yaml` 里分 `coils` 和 `holding_registers` 两个映射表。

### 10.3 关于 TensorRT

**Q: TensorRT engine 能跨 GPU 复用吗?**

> 不能。TensorRT engine 是针对具体 GPU 架构和 CUDA 版本编译优化的,不同 GPU 架构(如 Ampere vs Turing)需要重新编译。项目里 13 个 .engine 文件在换机器时都要重新从 ONNX 编译。

**Q: TensorRT 和 PyTorch 推理速度差多少?**

> 视模型而定,通常 TensorRT FP16 比 PyTorch FP32 快 2-5 倍。项目里 flag=6 用的是 .pt(PyTorch),flag=0-5 用的是 .engine(TensorRT),实际部署优先用 TensorRT 版本。

### 10.4 关于图像处理

**Q: 上万像素的大图怎么避免 OOM?**

> - `PIL.Image.MAX_IMAGE_PIXELS = None` 禁用 DecompressionBombWarning
> - 用 `tifffile` 流式读取大 TIFF
> - 切片后立即释放原图引用:`del img; gc.collect()`
> - SAHI 内部切片是内存视图,不会复制整图

**Q: 3250 DPI 是什么概念?**

> DPI = Dots Per Inch,3250 DPI 意味着每英寸 3250 像素。一块 200mm x 300mm 的 PCB,在 3250 DPI 下图像约 25600 x 38400 像素,单张图就是上亿像素。这就是为什么必须切片推理——直接送 YOLO 会 resize 到 640x640,小目标全部丢失。

### 10.5 关于依赖注入

**Q: 你的 DI 容器和 Spring 的 IoC 容器有什么区别?**

> Spring 的 IoC 容器是声明式的,通过 XML 或注解配置 bean,容器扫描装配。我的 Container 是命令式的,每个 property 手写创建逻辑。优势是简单直观无魔法,劣势是扩展时要改容器代码。如果用 `dependency-injector` 库可以实现声明式配置,但项目规模还不需要。

**Q: 延迟创建和预创建怎么选?**

> 延迟创建(lazy)的好处是启动快,按需加载;坏处是首次访问慢,且不是线程安全的。预创建(eager)的好处是启动时就发现问题,线程安全;坏处是启动慢。我的容器对仓储和服务用延迟创建(不依赖硬件),对 PLC/ACS 要求显式调用 `initialize_hardware()`(预创建 + 显式生命周期管理)。
